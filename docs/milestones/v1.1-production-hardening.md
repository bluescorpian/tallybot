# Milestone: v1.1 — Production Hardening

Target: reliable device connectivity in real-world venues and better operator visibility
when things go wrong.

> **Status (June 2026): CLOSED.** The **diagnostics** (Issue 2, firmware) and the **LED palette**
> (Issue 3) are done and verified. **WiFi-join reliability** (Issue 1) turned out to be dominated
> by venue access-point *policy* the device can't change (a weak-signal / min-RSSI kick at the
> second venue), so the project **pivoted to an ESP-NOW transport** ([roadmap](roadmap.md), item 3)
> as the near-term path to dependable venue connectivity. The remaining WiFi-join work is now a
> living runbook ([`docs/wifi-troubleshooting.md`](../wifi-troubleshooting.md)) and the in-app
> visibility work is **deferred to the [roadmap](roadmap.md)**. This milestone is no longer the
> active worklist — it's kept as a record of what shipped.

The full field-test context — what happened at each venue, ranked causes, and the
remediation detail — is in [`docs/archive/field-test-venue-1.md`](../archive/field-test-venue-1.md).

## Issue 1 — WiFi join reliability — firmware hardening shipped; deeper work deferred

Firmware-side fixes that landed (bench-verified):
- [x] TX power: full power first, conditional `WIFI_POWER_8_5dBm` fallback — only after a failed
  association, and **not** on deauth/leave reason codes 3/8 (low power worsens a min-RSSI kick)
- [x] Associated-verdict tracking: the diagnostics panel states "joined then dropped" vs "never
  joined", so a genuine AP kick is told apart from an auth/range failure
- [x] Keep-most-diagnostic-reason: our own portal-teardown disconnect can't mask the real failure
- [x] WiFi country / channel policy: manual South Africa channels **1–13** via
  `esp_wifi_set_country()` (the validated `esp_wifi_set_country_code("ZA")` path rejects "ZA")
- [x] Connect timeout + retries tuned (10 s / 2); WiFiManager pinned to 2.0.17
- [x] WPA3-SAE: confirmed enabled (transition mode is the arduino-esp32 default; noted in `setup()`)

Deferred to the [roadmap](roadmap.md) — WiFi is no longer the near-term transport:
- **Managed-AP policy** (min-RSSI kick / band-steering) — the venue-2 failure mode. Not solvable
  from the device, which is exactly what motivates the ESP-NOW pivot.
- **Password special-char URL-decode audit** on WiFiManager. The portal already echoes the stored
  password *length* (which surfaces a `#`-style truncation); the deeper decode audit is deferred.

> The earlier "bring-your-own AP" deployment recommendation has been **dropped** — it conflicts
> with the product's plug-and-play positioning. Venues with no usable WiFi are addressed by the
> ESP-NOW bridge (and the PC-hotspot option) on the [roadmap](roadmap.md), not by asking users to
> bring networking gear.

## Issue 2 — Operator visibility / diagnostics — device-side shipped; in-app deferred

Firmware-side fixes that landed:
- [x] WiFi disconnect reason captured, decoded, classified (auth-fail / not-found / DHCP /
  timeout), plus the associated-or-not verdict
- [x] Diagnostics panel on the SoftAP captive portal (verdict, last reason + raw code, SSID tried,
  RSSI, stored-password length, FW build stamp, MAC)
- [x] Last-boot diagnostics persisted to NVS — readable after reboot

Deferred to the [roadmap](roadmap.md) (needs sidecar + UI; tracked under "In-app device diagnostics"):
- **In-app logs panel** fed by the sidecar's existing NDJSON stream
- **Device→server diagnostic frame** (additive protocol message): RSSI / IP / uptime / reconnect
  count / FW version per device, shown on the board

## Issue 3 — LED state palette — done

- [x] Per-phase **device-local** colours + motion (amber WiFi family, cyan searching, connect-gap
  white breathe, boot self-test sweep) at 10% local brightness — firmware
- [x] **Server-driven** connected states: live/preview/idle steady, the fault flash, and the
  **unassigned white breathe** — all driven by the sidecar streaming frames over the wire
  (`app.ts` animation clock), so the firmware stays lean and just renders static `SET_COLOR`s
- [x] `SETUP_COLOR` magenta → white (the *unassigned* colour) in `app/sidecar/src/protocol.ts`
- [x] `docs/architecture.md` colour table references `docs/led.md`

Architecture decision (locked): **the firmware is lean; the server owns connected-state
animation.** Bring-up states animate locally only because no server is connected yet. See
[`docs/led.md`](../led.md).
