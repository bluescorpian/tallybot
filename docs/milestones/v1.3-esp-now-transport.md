# Milestone: v1.3 — ESP-NOW Transport

Target: tally lights work in venues with no usable WiFi. A USB-connected device can
be designated as a **bridge** in the app, at which point it relays tally commands to
other lights over ESP-NOW — no AP, router, or network infrastructure required.

All devices run the same firmware. Bridge behaviour is a mode set in the UI, not a
separate firmware build.

The design decisions behind this transport are documented in
[`docs/milestones/roadmap.md`](roadmap.md#3-esp-now-transport).

**Builds on v1.2.** This milestone is being developed immediately after v1.2's USB provisioning
channel (USB comms + No-TX + WiFi modes). The bridge is a USB-connected device that speaks the
[USB-serial protocol](../spec/usb-serial-protocol.md), and ESP-NOW is the fourth step in the
incremental plan (see [v1.2 implementation order](v1.2-zero-friction-onboarding.md#implementation-order)):

> USB comms → No-TX → WiFi provisioning → **ESP-NOW**

The ESP-NOW path uses the same `SET_TRANSPORT` command as WiFi/No-TX (value `2`) and simply
omits SSID/password. Two protocol extensions are **new here and not yet specced** — a v1.3 spec
should design them before coding:

1. **A transport-mode value for ESP-NOW** beyond v1.2's `{No-TX, WiFi}`, plus a bridge
   designation.
2. **Relay addressing** — v1.2's USB `SET_COLOR` targets the single directly-connected device,
   but a bridge relays to many lights behind one USB endpoint, so commands need a target-MAC
   wrapper. Bridged devices surface through the same `CompositeDeviceServer` seam v1.2 introduces.

**Delivery reliability is already handled.** ESP-NOW is fire-and-forget — a dropped `SET_COLOR`
would otherwise strand a light on a stale colour. v1.2 pre-empts this: the sidecar re-asserts every
device's current colour on a ~1 s keyframe tick for *all* transports (see `SidecarApp` /
`REFRESH_PERIOD_MS`, documented under SET_COLOR in [`architecture.md`](../architecture.md)). A lost
packet self-heals on the next tick, so the ESP-NOW path needs **no** per-message ack/retry — treat
the relay as a dumb byte-forwarder and let the keyframe cover loss.

## Requirements

- Any USB-connected device can be designated as a bridge in the UI; doing so puts
  it into bridge mode and makes it relay tally commands to nearby ESP-NOW lights
- Tally lights can be provisioned in ESP-NOW mode and operate without joining any
  WiFi network, receiving commands via the bridge
- Transport mode (WiFi or ESP-NOW) is selected at provisioning time and stored on
  the device
- Multiple ESP-NOW lights operate simultaneously through a single bridge
- The app onboarding wizard handles both transport paths; the ESP-NOW path requires
  no SSID or password
- WiFi and ESP-NOW devices coexist in the same session without conflict
- Existing WiFi-only deployments are entirely unaffected

---

## Acceptance criteria

- A USB-connected device designated as bridge in the UI relays commands to nearby
  ESP-NOW lights with no WiFi network present
- Multiple ESP-NOW lights show correct live/preview/idle state simultaneously
- Onboarding wizard offers WiFi vs ESP-NOW choice; ESP-NOW path has no credential step
- A mixed session (some WiFi devices, some ESP-NOW devices) works correctly
